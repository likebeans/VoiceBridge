# 声桥容量与延迟验证

2026-11-04，在本机 macOS ARM64、Python 3.13.12 上验证。服务、模拟上游和负载客户端分属三个进程。结论：默认 100 会话上限在本次模拟测试中可用，新增监控和容错没有显示明显的稳态转发开销；真实网关的并发配额、长时间稳定性和部署机器容量仍需在对应环境验证。

## 100 会话对照

每会话 10 秒 PCM16LE / 16 kHz / 单声道音频，100 ms 分片，5 秒内均匀启动 100 会话。模拟上游建连延迟 30 ms，累计每 300 ms 音频产生一个中间快照，停止后延迟 150 ms 完成。

| 版本 / 次数 | 完成 | 峰值并发 | start→ready p50 / p99 | 第一包→首字 p50 / p99 | stop→done p50 / p99 | CPU 平均核数 | 峰值 RSS |
|---|---:|---:|---:|---:|---:|---:|---:|
| 改动前，1 | 100/100 | 100 | 32.11 / 36.07 ms | 200.66 / 204.15 ms | 151.63 / 170.01 ms | 0.144 | 56.33 MiB |
| 改动前，2 | 100/100 | 100 | 32.04 / 37.96 ms | 200.70 / 208.65 ms | 151.91 / 155.64 ms | 0.147 | 57.69 MiB |
| 新版，1 | 100/100 | 100 | 31.69 / 37.92 ms | 200.64 / 202.25 ms | 151.81 / 158.65 ms | 0.147 | 55.20 MiB |
| 新版，2 | 100/100 | 100 | 32.22 / 35.44 ms | 200.82 / 202.76 ms | 151.52 / 154.62 ms | 0.144 | 57.19 MiB |

新版两轮每会话均发送 320000 字节，收到 37 个文字快照和 `done`，以 1000 关闭；服务报告音频时长与发送字节数一致。扣除模拟上游固定延迟后的额外耗时只是近似值：建连 p50 为 1.69 / 2.22 ms，收尾 p50 为 1.81 / 1.52 ms。

120 会话同时接入、上限 100 的突发场景：100 会话完成，20 会话拒绝。改动前拒绝表现为 HTTP 403；新版拒绝收到 JSON `server_busy` 后以 1013 关闭，调用方能区分容量不足。新版峰值 RSS 61.89 MiB，start→ready p99 90.24 ms，stop→done p99 170.79 ms。突发与平滑启动负载不可直接比较。

## 更高消息频率

100 会话、每会话 60 秒音频、20 ms 分片（满载阶段每秒约 5000 条输入音频消息），5 秒内均匀启动：100/100 完成，峰值 100 会话，服务 CPU 平均 0.350 核、峰值 RSS 56.59 MiB。每会话收到 220 次文字快照，音频时长一致。start→ready p99 为 36.94 ms，第一包→首字 p99 为 282.89 ms，stop→done p99 为 155.59 ms。

负载客户端的音频发送调度滞后 p99 为 **13.82 ms**，超过脚本设定的 20 ms 分片时长 20% 告警阈值。客户端最高一秒 CPU 约 0.25 核，没有达到单核饱和，但本机调度噪声已经可见。因此这次结果证明处理正确性和资源占用，不作为严格延迟上限或长期压力验收。20 ms 分片在约 280 ms 后达到 300 ms 模拟出字阈值，和 100 ms 分片的约 200 ms 指标不能直接比较。

## 提前发送音频

同一新版服务、100 会话、每会话 3 秒音频，2 秒内启动，模拟上游建连固定为 800 ms：

| 客户端策略 | 完成 | start→首次非空文字 p50 | 峰值 RSS |
|---|---:|---:|---:|
| 等 ready 后发送 | 100/100 | 1003.15 ms | 57.52 MiB |
| start 后立即发送 | 100/100 | 802.45 ms | 63.53 MiB |

首次文字约提前 200.70 ms。提前发送组每会话约有 0.9 秒音频在 ready 前进入服务缓冲，最终音频时长均一致。此实验验证建连和录音重叠的作用，不能推导真实模型一定降低同样的延迟。浏览器示例仍使用等 ready 的兼容流程；需要提前发送的调用方应按协议配置有限缓冲。

第一包→首字不适合单独比较这两种策略：等 ready 的客户端是在建连完成后才发第一包，提前发送的客户端把建连时间也计入了此区间。对比用户等待应看 start→首字；前端还需单独测麦克风授权、采集和网络耗时。

## 故障与停机

- 模拟前三次 WebSocket 握手返回 503，3 个会话各重试一次后全部完成，提前发送的音频没有丢失。任务协议内的 `ServiceUnavailable` 等明确临时故障同样可在启动时重试；真实本地 WebSocket 回归用例验证第二次恢复且音频只发给成功的尝试，鉴权失败和限流则只尝试一次。
- 模拟识别到 1 秒音频后返回 `task-failed`，3 个会话均得到 `upstream_error`、1011 关闭，没有伪造 done 或重放音频。
- 自动化测试覆盖鉴权拒绝和限流不做同供应商重试、每次尝试和整体连接超时、启动前兜底、ready 切换竞态、缓冲限额及断连释放。
- 真实子进程 SIGTERM 验证：readiness 变为 503，新会话得到 `shutting_down`，已有音频继续转发并正常 done；耗尽停机等待窗口则关闭剩余会话。
- Docker 构建成功，非 root 用户运行；使用假密钥和禁网容器验证 HEALTHCHECK 为 healthy、readiness 正常，测试容器已清理。

## Fun-ASR 参数和小样本延迟

另对真实 MaaS 网关做了短合成音频参数探测，最多两个会话同时运行，单段最长 7.95 秒。39 次尝试中 38 次完成，1 次取消；没有做识别质量评估，也没有对真实网关做 100 并发压测。

未知参数也会被静默接受，因此成功收到 `task-started` 不代表参数有效。

- `max_sentence_silence`：200 / 400 / 800 ms 在相同音频中的首次句末分别约为 3.620 / 3.880 / 4.386 秒，2000 / 5000 ms 则把跨停顿内容合成一句。证实影响断句与定稿；服务仍保持默认 400 ms、可配置 200–2000 ms，避免更长等待成为默认行为。
- `semantic_punctuation_enabled`：只观察到空事件数变化，非空快照和最终标点相同；两次重复没有一致的首字优势，不暴露为性能开关。
- 标点、ITN、语气词过滤及候选别名：开关两侧无可验证的预期文字变化，不暴露。
- 无效 `vocabulary_id` 未触发错误，无可用真实词表验证其效果，暂不暴露。
- `language_hints` 被接受，但不能当作强制语言约束。保留已有语言提示接口。
- 12 秒无音频的观察期内连接仍存活，`heartbeat` 开关无可见差异，不能据此推断更长空闲时间的行为。

两次顺序发送、100 ms 分片的真实网关基线：第一包音频→首次非空文字 475 / 493 ms，finish-task→task-finished 140 / 139 ms。这些是合成短音频的小样本，不是 SLA、分位数或真实用户录音的平均值。

## 复现

脚本仅使用本机模拟上游和假密钥，服务从临时空目录启动，不读取项目 `.env`，进程退出后自动回收。`--src-path` 会验证实际导入目录；可指向保留的旧源码副本进行对照。

```bash
# 100 会话，平滑启动
uv run python scripts/loadtest.py --src-path src \
  --connections 100 --duration 10 --ramp 5 --json-out /tmp/asr-100.json

# 突发满载
uv run python scripts/loadtest.py --src-path src \
  --connections 120 --max-connections 100 --duration 10 --ramp 0

# 较慢建连时的提前上传对照：各运行一次，有/无 --early-audio
uv run python scripts/loadtest.py --src-path src --connections 100 \
  --duration 3 --ramp 2 --mock-start-delay-ms 800 --early-audio

# 更高分片频率
uv run python scripts/loadtest.py --src-path src --connections 100 \
  --duration 60 --ramp 5 --chunk-ms 20

# 连接失败重试和中途失败
uv run python scripts/loadtest.py --src-path src --connections 3 \
  --duration 2 --ramp 0 --mock-reject-first 3 --early-audio
uv run python scripts/loadtest.py --src-path src --connections 3 \
  --duration 2 --ramp 0 --mock-fail-after-seconds 1
```

统计口径：CPU/RSS 来自 POSIX `wait4`，覆盖服务整个进程生命周期，包括启动和退出；CPU 平均核数为该 CPU 时间除以负载运行时间。负载客户端单独记录 CPU 与调度延迟。测试 PCM 是预生成音频，每个分片在时间窗口开头发送，因此 100 ms 分片在约 200 ms 后已发送累计 300 ms 音频，模拟首字约 200 ms 是预期值。所有时间戳使用单调时钟。服务、模拟上游与客户端共享一台机器，结果包含调度和本地网络噪声。

测试中 Uvicorn 的旧 websockets 后端和 Starlette TestClient 有依赖弃用提示；协议测试均通过。本次保留已经验证的传输队列与消息上限，未混入 WebSocket 后端迁移。
